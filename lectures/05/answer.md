# 第5回 解答

## 演習

- 回答モデル（実行時の`[model]`）：`gemini-3.5-flash-lite`
- 比較した質問：`第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？`
- 対象資料（全文投入と他の方式で範囲が違う点も記録）：
  - ベクトル／Tree／Graph：第1〜3回の本講義（`lec01-main`〜`lec03-main`）
  - 全文投入：教材JSONの全資料（今回は入力227,971文字。入力上限エラーにはならなかった）

### 各方式の結果

| 方式 | 回答の要点・正しさ | 引用ページと根拠 | 時間（秒） | 入力／出力トークン数 | モデル応答回数 | 生成API推定費用（USD） |
|---|---|---|---|---|---|---|
| 全文投入 | LoRA＝元の重み固定・差分行列を学習、QLoRA＝4bit圧縮を加える、と正しく述べつつ、宿題の答えを出しすぎないような言い回しになった | p.51・p.52 を参照として挙げる | 3.55 | 117,025 / 189 | 1 | 0.004624 |
| ベクトル検索 | 同上で簡潔に正解。根拠ページも妥当 | 第2回・PDF p.51, p.52 | 6.06 | 3,028 / 156 | 2 | 0.001298 |
| Tree | 同上で詳細に正解。付箋の比喩まで含めている | 第2回・PDF p.52（最終的に全文取得） | 7.41 | 9,214 / 341 | 5 | 0.003617 |
| Graph | 同上で正解。p.51・52を引用 | 第2回・PDF p.51, 52 | 6.70 | 5,771 / 221 | 2 | 0.001736 |

- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  - 上位に **PDF p.52「LoRA と QLoRA」** と **p.51「PEFT」** が出た。p.52本文に「元の重みは固定し、小さな差分だけを学習」「元の重みを4bitに圧縮」があり、質問の根拠として十分
  - p.60・61・47もヒットしたが、演習手順や一般論で、今回の答えの核心ではない（似た用語のページと根拠ページを区別できた）
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  - ベクトル：`search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` 1回
  - Tree：`browse_tree` を4回（ルート → `lec02-main` → `lec02-main-s045` → `lec02-main-p052`）。目次の先頭文から p.52 を選べていた
  - Graph：`search_graph({'query': 'LoRA QLoRA 固定 学習'})` 1回（seeds に p.52）
  - 全文投入：ツール呼び出しなし（資料を一括入力）
- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  - 今回の質問では主要方式すべてで p.52 系の根拠に到達でき、答え自体は揃った
  - 全文投入は必要なページを含められる一方、入力トークンが約11.7万と大きく、費用も他方式より高い。また回答がやや遠回しで、根拠を十分に使い切っていない印象
  - ベクトル検索の上位には演習スライドなど不要なページも混ざるが、モデルが p.51/52 を選んで使えていた
- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - **通常のベクトル検索**を基本にしたい。正解に必要な根拠を低コスト・少ない応答回数で取れた
  - Treeは目次をたどる過程が分かりやすいが、応答5回・時間・トークンが増える
  - Graphは今回ベクトルに近い結果。比較は同一質問・同一モデル1回ずつの観察であり、方式全体の優劣を断定するものではない
- 気づき・疑問：
  - 「全部渡す」より「必要なページだけ渡す」方が、費用と使い方の両面で有利な場面がある
  - 検索ヒットと、回答に使った根拠は一致するとは限らない（ヒットの質と、モデルの利用の質を分けて見る）

## 宿題

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/config.py` の `RAG_TOP_K` だけを **5 → 2** に変更（指示文・docstring・索引は未変更）
  - 同じ質問・同じモデル（`gemini-3.5-flash-lite`）・同じ対象資料で、通常のベクトル検索（`--trace`）を再実行
- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 質問：演習と同じ LoRA / QLoRA の質問
  - モデル：`gemini-3.5-flash-lite`
  - 方式：`--trace`（`search_materials`）
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：

| | TOP_K=5（変更前） | TOP_K=2（変更後） |
|---|---|---|
| ツール呼び出し | `search_materials` 1回 / query=`LoRA 固定 学習 QLoRA 加える` | 同様に1回 / ほぼ同じ query |
| 回答の正しさ | 正解（固定＝元の重み、学習＝差分、QLoRA＝4bit圧縮） | 同様に正解 |
| 引用根拠 | 第2回・PDF p.51, p.52 | 第2回・PDF p.51, p.52 |
| 時間（秒） | 6.06 | 5.40 |
| 入力／出力トークン | 3,028 / 156 | 1,741 / 165 |
| モデル応答回数 | 2 | 2 |
| 生成API推定費用（USD） | 0.001298 | 0.000935 |

- 改善した例と、残る失敗・制約：
  - 件数が減っても今回の質問では核心の p.51/52 が残るため、答えの質はほぼ維持しつつ入力トークンと費用が下がった
  - 一方、根拠が上位以外にしかない質問では、TOP_K を下げると取りこぼす可能性がある（今回は1問だけの観察）
- 気づき・疑問：
  - 検索件数は「多いほど良い」ではなく、質問に対して十分な根拠が入る最小付近を探るパラメータだと感じた
  - 変更前後でツールの呼ばれ方（回数）は変わらず、渡す本文量（入力トークン）が主に変わった
